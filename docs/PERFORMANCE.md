# 首次访问与增量索引

## DeSQL 中实际发生了什么

`message-ledger/fast-mainnet.js` 的 `makeFastSession()` 每次新页面会话从空的 `baseline / activation / previous / verifiedReader` 开始。

第一次 `refresh()` 调用 `verifyBaseline()`，它创建最终确认 reader 并重放旧消息账本，重新计算迁移余额承诺；之后验证激活消息，再重放 FAST 规则。`mainnet.js` 已按 Hub 和收件端点过滤 Sent 日志，并复用当前会话中已认证的读结果。因此“每次都扫全链”并不精确：热点是重复读取业务信箱历史、逐条验证历史代码与存储、再重放；刷新后的缓存不跨浏览器会话保存。

## 本项目实际采用的做法

合同没有可花费余额，不需要全局排序防止双花。每份合同可以独立验证，因此采用交易引用图：

```
offer(正文 + 发起方笔迹 + 发起方钱包签名)
   ↑
accept(offer 的链和交易 + 对方笔迹 + 对方钱包签名)
   ↑
seal(完整正文 + 双方笔迹 + 双方钱包签名 + offer/accept 定位)
```

邀请只读 offer，回签读 accept 与 offer，归档读 seal、accept、offer。无需遍历之前的其他合同。实际 RPC 数量还有每笔交易的代码、持有人、事件 / 存储和最终确认检查，延迟取决于节点，不承诺固定秒数。

“我的合同”不需要完整列表后才能用。以当前容器 endpoint / address 查询：

1. `inboxCount` / `outboxCount` 获取上限。
2. 首次仅取尾部 12 条；点击更早记录再向前翻页。
3. 本地保存 `[low, high)` 及查询时的最新共同区块哈希；再次打开只读 `high` 后新增的最多 12 条。新交易无需等最终确认才能进入定位列表。
4. 用分页得到的精确区块过滤 Hub 的 `Sent` 日志；收件过滤 `to`，发件过滤 `from`。
5. 对分页每条记录核对 digest；缺失 / 重复日志导致该页失败，不静默推进游标。
6. 核对原缓存锚点仍在规范链；不匹配时抛弃缓存窗口并重建最新页。
7. 列表缓存不代表真伪。打开任何条目都重新执行 reader。

测试有 100 万条信箱的窗口计算，首次仍然 12 条；另有读图测试断言邀请 / 回签 / 归档分别 1 / 2 / 3 次交易回执定位，且没有历史 `eth_getLogs` 扫描。后者并非主网速度基准。

签署等待与 RPC 读取耗时分开处理。X Layer `finalized` 可能比最新区块落后十几分钟，因此业务放行改为 12 个后续区块（BSC 24 个）、两家节点一致及最新头新鲜度校验。正常网络目标一分钟内，实际包含打包、确认深度、10 秒轮询和校验耗时；不承诺链故障或节点限流时达到该目标。正文在打包并通过数据核验后即可显示；最终确认继续独立跟踪。

## 对“只验证余额根”的判断

一个哈希只能证明“某份状态与该哈希一致”，不能证明状态是按照真实交易和规则正确算出来的。Merkle 路径可以证明账户属于某个根，但不能证明根的来源正确；更不能只检查单个账户来发现其他账户双花或全局排序错误。

要优化原 DeSQL，建议分阶段实施：

1. 将已认证交易、区块锚点、确定性状态快照和版本放入 IndexedDB，回到同一设备时仅核验连续性并处理增量。保留重组回滚窗口。缓存不跨未验证的代码 / 规则变更复用。
2. 增量状态机维护余额 / nonce；不要每轮再次遍历全部已确认记录；短确认尾部单独回放。
3. 首次新设备仍需要验证到可信检查点的历史。可提供内容寻址快照作为下载加速，但在信任模型不变时需要对其来源或计算正确性验证。
4. 若目标是新设备也立即信任余额根，需要协议级可信检查点、共识认可承诺、可验证计算或零知识状态转换证明等机制，并明确引入的信任假设。不能只加缓存字段 `verified: true` 或服务器签一个根就称完全独立验证。

此次只完成电子合同独立索引，不修改 DeSQL 账本，避免改变其资产有效性规则。
