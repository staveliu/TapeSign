# 链上签约使用指南

链上签约是 TapeSign 链上公证处的首页功能：甲乙双方对同一份富文本合同手写签名，并用各自的钱包确认；发起人最后将正文和双方签名一起归档到链上。单方对文字或图片声明归属，请使用 [链上公证](NOTARY.md)。

当前合同协议为 `TAPESIGN-2`，支持 X Layer（196）和 BSC（56）。本指南对应应用 0.2.0；旧版 `TAPESIGN-1` 合同继续使用原客户端，不迁移或重签历史记录。

## 开始之前

1. 使用支持浏览器钱包的钱包环境，连接自己的钱包。发送交易需要对应链上的原生 gas。
2. 在产品顶部选择自己的 TapeOut 容器，可从钱包列表选择，也可手动输入短 ID 或带 `.tape` 后缀的 ID。客户端核验绑定与持有人，手动输入不会跳过身份检查。
3. 当前容器供签约和公证共用，无需在每个功能内重复输入；切换钱包后需要重新选择。未选择时，右上角以红字提示“请先选择容器”。
4. 准备对方的容器 ID，明确自己是甲方还是乙方。任意一方都可以发起，发起人不一定是甲方。

双方可以使用不同支持链上的容器。合同记录各方的容器与持有人身份，交易在当前操作方容器所属链发送。

## 页面入口

| 标签页 | 用途 | URL 锚点 |
| --- | --- | --- |
| 发起合同 | 编辑标题、正文与双方信息，预览并签署 | `#contract/create` |
| 打开 / 核验 | 通过合同链接或链与交易哈希读取、核验和继续签署 | `#contract/open` |
| 我的合同 | 查询当前容器相关合同，按合同号归并阶段 | `#contract/history` |

切换标签页会更新 URL 锚点，刷新和浏览器前进 / 后退会恢复相应页面。合同分享链接中的 `chain` 与 `tx` 定位交易；标签页切换会保留这些查询参数。

## 一份合同的完整流程

### 1. 发起人起草

在“发起合同”填写标题，选择自己的甲乙方角色，输入对方容器，编写富文本正文。编辑器支持段落、标题、列表、加粗、斜体和下划线；正文使用结构化数据，不接受任意 HTML 或图片附件。

预览时核对全文、双方容器、角色及钱包身份，再冻结正文进入签署。草稿保存在当前浏览器；正式签署后改变正文会改变合同指纹，不能沿用旧签名。

### 2. 发起人手写并发送邀请

用鼠标或触屏在签名框内写下签名，可以撤销一笔或清空重写。之后按钱包提示签署 EIP-712 同意消息，再确认 `offer` 交易。

手写笔迹是合同中可阅读的签名图形；钱包签名把笔迹、正文、身份、角色及签署阶段绑定在一起。两步都需要完成，仅画出笔迹不代表交易已提交。

客户端为合同生成与 UTC 毫秒时间关联、包含 128 位随机标识的 `TS-…` 合同号。提交后保存邀请链接交给对方。拿到交易哈希只表示已提交，不表示已经打包、核验或最终确认。

### 3. 对方打开并回签

对方直接打开邀请链接，连接自己的钱包并在顶部选择合同中约定的容器。客户端按链与交易哈希定位邀请、显示正文，并独立检查链上证据。达到签署条件后，对方阅读同一份合同，手写签名、确认钱包同意消息并发送 `accept` 交易。

回签引用原邀请及合同指纹，不能通过修改本地页面把另一份正文当成原合同签署。收到的邀请应核对正文、双方身份和链上核验结果。

### 4. 发起人发现回签

发起人留在原合同页面，或打开“我的合同”，客户端会查询缓存及相关链上的容器信箱，发现后续回签。通常无需对方再发回传链接；回传链接仍可作为直接定位入口。

刷新约每 10 秒尝试一次，实际等待还取决于交易打包、索引和 RPC 响应。刚发送后没有立刻出现，不代表对方需要再次签署。

### 5. 发起人归档

客户端独立核验双方签署及前序引用后，由原发起人确认并发送 `seal`。这一笔归档交易包含完整正文、双方身份、双方笔迹和钱包签名，以及邀请、回签的链与交易定位。

**双方已经签署与完整归档是两个阶段。** 收到 `accept` 后仍需原发起人发送 `seal`；另一方不能代替原发起人执行当前协议的归档步骤。

### 6. 双方查询与保留证据

双方可从“我的合同”或归档链接读取同一份合同，查看签署与确认状态。客户端通过独立链上核验后，可以打印、由浏览器保存为 PDF，或导出 JSON 证据。建议同时保留合同链接、JSON 和可信客户端版本清单。

## 三个阶段分别存什么

| 阶段 | 操作者 | 主要链上数据 |
| --- | --- | --- |
| `offer` 邀请 | 发起人 | 合同号、完整文档、双方身份、发起人的笔迹和钱包同意签名 |
| `accept` 回签 | 另一方 | 同一合同号、文档指纹、原邀请引用、另一方的笔迹和钱包同意签名 |
| `seal` 归档 | 原发起人 | 完整文档、双方原始同意数据、邀请与回签引用 |

正常完整流程有 **3 笔业务交易**：发起人承担邀请与归档两笔，另一方承担回签一笔，各自在所属链支付 gas。钱包同意签名与发送交易是不同操作；页面中的 RPC 读取次数也不等于业务交易数。

“我的合同”按同一合同号归并这三个阶段，因此显示一份合同，而不是三份合同。交易本身不会被合并或删除。相同编号出现不同文档指纹或不兼容的签署分支时，应查看冲突提示及原始引用，不能只相信最新一笔交易。

## 核验状态怎么读

| 状态 | 含义与处理 |
| --- | --- |
| 交易已提交 / 等待确认 | 已拿到哈希，链上收录或确认可能仍在等待；保留原链接，不重复发送 |
| 签名校验通过的缓存正文 | 可先阅读经过签名检查的预览；不代表独立链上核验已完成，不能据此回签、归档或导出 |
| 链上证据已核验，确认深度不足 | 继续等待所需确认；原件可见不等于签署按钮已开放 |
| 达到短确认条件 | 所有依赖证据一致且符合深度与新鲜度要求，可继续回签或归档；最终性另行显示 |
| 最终确认 | 核验所依赖的交易已达到链报告的最终确认条件 |
| RPC 不可用 / 证据异常 | 网络故障会重试；数据分歧或校验不通过时停止授权操作，不能视为成功 |

浏览器短确认门槛为 X Layer 后续 **12 个区块**、BSC 后续 **24 个区块**；要求两个独立 RPC 核验槽位结果一致，最新区块头足够新，且全部依赖交易满足条件。已最终确认的交易可直接满足确认条件。

短确认是继续业务的条件，不是最终性证明，也不承诺一分钟内完成。钱包等待、节点限流、链重组和历史状态读取故障都可能延长时间。

## 缓存如何加速

邀请链接直接定位交易，避免为了打开一份合同先扫描所有历史。“我的合同”首次对每个相关信箱只读取最近 12 条，之后按游标增量读取，较早记录按需加载。

可选缓存保存合同记录，提供预览、合同号归并及回签 / 归档定位。服务器的 `ready`、`verified` 或 `finalized` 字段不能代替客户端独立核验。合同流程仍可在缓存不可用时通过有效 RPC 查询与核验；公证新提交的缓存要求见 [公证指南](NOTARY.md)。

索引与 RPC 复用规则见 [合同缓存设计](CACHE-V2.md)。

## 独立核验与备份

在项目目录使用合同命令行核验器：

~~~sh
node scripts/verify.mjs "合同完整链接"
node scripts/verify.mjs "evidence.json"
node scripts/verify.mjs 0x交易哈希 196
~~~

它根据定位重新读取链上原件，默认要求最终确认，不要求原业务网站或缓存在线，但需要可用且支持历史状态的 RPC。该脚本用于合同，不是公证的通用核验器；公证请使用页面中的独立核验入口。

PDF 是可读副本，JSON 是证据与定位的备份；两者都不替代重新核验链上证据。TapeOut 站点内容可以更新，版本路径也不是只读权限，因此应另行保存可信源码、版本清单和客户端副本。

## 范围、隐私与大小

- **合同正文及手写笔迹明文公开上链。** 当前没有加密合同模式；不要用不应公开的资料做测试。
- 仅支持甲乙双方，不提供多人审批、附件、撤销、作废、修订工作流或 ERC-1271 合约钱包签名。
- 正文结构最多 6,500 UTF-8 字节；字节数包含结构开销，不等于汉字个数。
- 每份笔迹最多 30 笔、220 个点且不超过 2,300 字节；完整消息载荷不超过 16,000 字节，最终以校验结果为准。
- 签约身份在发起时确定；转让容器不会自动替换原签约人或转让合同主体，后续操作仍受原约定身份与链上持有人检查约束。
- 核验展示容器、钱包签名和链上记录的一致性，不提供对现实身份、内容真实性或法律效力的判断。

## 常见问题

| 情况 | 处理方式 |
| --- | --- |
| 只显示“交易已提交”，没有正文 | 核对链接中的链和完整交易哈希；等待打包与回读。已有缓存正文时可先预览；RPC 不可用时保留链接等待重试，不重新发合同 |
| 能看正文却不能回签或归档 | 检查是否仅为缓存预览、所选容器是否正确、所有依赖交易是否达到确认条件 |
| 对方已签，发起人暂时看不到 | 打开原邀请或“我的合同”刷新；核对对方回签的链与哈希，也可用回传链接直接定位，不必让对方再次签署 |
| 提示 `missing trie node`、归档节点授权或 HTTP 403/502 | 检查指定链和 RPC 方法，配置支持历史状态的节点；改配置后重建客户端 / 缓存，不能跳过历史身份检查 |
| 钱包发送结果未知 | 先查钱包活动及交易哈希，通过已有恢复流程核对；不要清除待确认记录后再次付款 |
| 合同较早，列表暂未出现 | 加载更早记录或直接打开原链接；首屏与缓存尚未收录不代表链上不存在 |
| 提示客户端版本不兼容 | 使用合同所绑定且可核验的兼容版本；不要修改已签文档中的版本字段 |

开发实现与证据字段见 [协议说明](PROTOCOL.md)；节点、缓存及发布配置见 [配置](CONFIGURATION.md) 和 [部署](DEPLOYMENT.md)。
